# 0024. 앱 검사는 PR에서 바뀐 영역만 돌리고, Rust 의존성 검사는 main에서만 돌린다

- 상태: 채택 (2026-11-27)
- 근거: [0012](0012-skeleton.md), [0020](0020-split-ci-jobs.md), [0022](0022-apt-deb-cache.md)
- 대체: 0020의 "세 작업은 늘 함께 돈다"

## 상황

0020에서 앱 검사를 작업 셋(화면, 의존성, Rust)으로 나눴다. 그런데 `app/**`가 바뀌면 셋이 늘 함께 돌았다. 화면만 고친 PR도 Rust 작업(apt 설치, 컴파일, 테스트)이 끝나야 결과가 나왔다.

2026-11-25 main 실행(45618122074)의 작업별 시간:

| 작업 | 걸린 시간 |
|---|---|
| 의존성 | 19초 |
| 화면 | 65초 |
| Rust | 157초 |

앞으로 `app/ui/`만 고치는 화면 개편 PR이 연달아 올라온다. 통합 테스트가 들어오면 Rust 작업은 더 길어진다.

작업 이름(화면, 의존성, Rust)도 무엇을 검사하는지 드러나지 않았다. "의존성"은 Rust 라이브러리만 보는데 이름에 없었다.

## 선택지

**바뀐 영역을 고르는 방법**

1. 워크플로를 영역마다 파일로 나누고 `paths`로 거른다: 단순하다. 다만 한 작업이 실패해도 다른 파일의 작업은 멈추지 않는다. 생성 파일처럼 두 영역에 걸친 파일은 두 곳에 적어야 한다.
2. 바뀐 파일을 골라 주는 외부 액션: 0020에서 피한 외부 의존이 늘어난다.
3. **첫 작업이 `git diff --name-only`로 바뀐 파일을 보고 돌릴 작업 목록을 만든다**: 외부 액션이 없다. 매트릭스와 `fail-fast`를 그대로 쓴다.

**Rust 의존성 검사(cargo-deny)를 언제 돌릴까**

1. 의존성 파일(`Cargo.toml`, `Cargo.lock`, `deny.toml`)이 바뀐 PR에서
2. 1에 더해 주 1회 정해진 시각에: 새 취약점 공지는 코드가 안 바뀌어도 생긴다.
3. **main에 머지될 때만**: 실패하면 그때 보안 이슈와 PR을 따로 낸다.

## 결정

**PR에서는 바뀐 파일을 보고 화면과 Rust 중 필요한 작업만 돌린다. main에 머지되면 셋 다 돌린다. Rust 의존성 검사는 main에서만 돈다.**

| 바뀐 파일 (PR) | 화면 | Rust |
|---|---|---|
| `app/ui/**`, `.node-version` | O | |
| `app/ui/src/api/generated/**` | O | O |
| `app/{domain,server,launcher}/**`, `app/rust-toolchain.toml`, `app/clippy.toml`, `app/.cargo/**` | | O |
| 크레이트의 `Cargo.toml`, `app/Cargo.lock` | | O |
| `app/Cargo.toml` (화면이 버전 번호를 여기서 읽음) | O | O |
| `justfile`, `check.yml`, `.github/ci/**`, 위에 없는 `app/` 파일 | O | O |
| 문서(`*.md`), `app/deny.toml`, 다른 워크플로 | | |

- 고르는 규칙은 `.github/ci/pick-checks.sh` 한 곳에 둔다. 같은 스크립트를 내 PC에서 파일 목록을 넣어 시험할 수 있다.
- 첫 작업 "바뀐 파일·파일 이름"은 파일 이름 검사(`check-names`)도 돌린다. 저장소 전체를 보는 검사라 영역과 상관없다.
- PR이 아니거나 바뀐 파일을 읽지 못하면 셋 다 돌린다.
- 고른 작업이 없으면 검사 작업을 건너뛴다.
- 고른 작업은 지금처럼 매트릭스 하나로 함께 돌리고, 하나가 실패하면 나머지를 취소한다(0020).
- 내 PC의 `just check`는 그대로 전부 검사한다.
- 작업 이름을 바꾼다: 워크플로 "앱 검사", 작업 "바뀐 파일·파일 이름", "앱 화면 (React)", "앱 본체 (Rust: 도메인·서버·런처)", "Rust 의존성 (보안·라이선스)". 웹사이트 검사 작업은 "웹사이트 (site)"로 바꾼다.

## 이유

- 화면만 고친 PR은 화면 작업(약 1분)만 기다린다. Rust만 고친 PR은 화면 작업을 돌리지 않는다.
- 생성 파일은 화면 폴더에 있지만 Rust 타입과 맞아야 한다. 생성 파일이 바뀌면 Rust도 돌려 `check-bindings`가 본다.
- 어디에 닿는지 모르는 파일은 덜 검사하는 쪽으로 틀리지 않게 둘 다 돌린다.
- main에서 셋 다 돌리면 여러 PR이 합쳐진 상태를 한 번 더 본다. Rust 캐시와 apt 캐시도 main에서만 저장하므로(0022) 캐시가 낡지 않는다.
- 정해진 시각 실행은 main 검사와 같은 동시 실행 묶음에 들어가 서로를 취소할 수 있고, 정각에는 늦어지거나 빠질 수 있다(GitHub 문서). main 머지가 잦아 그때 보면 충분하다고 유지보수자가 판단했다.

## 결과

**좋은 점**
- 화면 개편 PR이 Rust 작업을 기다리지 않는다.
- 외부 액션이 늘지 않는다.
- 작업 이름으로 무엇을 검사하는지 알 수 있다.

**감수할 점**
- 취약하거나 라이선스가 맞지 않는 라이브러리를 넣은 PR도 머지된 뒤 main에서야 실패가 보인다.
- 머지가 없는 동안에는 새 취약점 공지를 알지 못한다.
- 고르는 규칙에 빠진 경로가 있으면 PR에서 검사가 덜 돈다. main에서는 셋 다 돌아 그때 드러난다.
- 작업이 하나(바뀐 파일 보기) 늘어 전체 시간이 몇 초 길어진다.
- 나중에 main 보호에서 필수 검사를 켜면, 건너뛴 작업을 어떻게 볼지 정해야 한다.
- 통합 테스트가 들어오면 고르는 규칙과 작업을 다시 본다.
