# 0002. 호스트 PC 한 대가 DB를 갖고, 호스트는 파일로 넘긴다

- 상태: 채택 (2026-11-14)
- 근거: [실험 01](../../spikes/01-sqlite-concurrency/), [0001](0001-app-form.md)

## 상황

회원, 강좌, 신청 데이터는 여러 직원이 동시에 읽고 쓴다. 업무 규칙(정원, 최대 신청 개수, 같은 과목 중복 금지)은 데이터 전체를 보고 판단해야 한다.

실험 01에서 서버 하나가 SQLite DB를 갖고 여러 직원의 요청을 받는 구조를 시험했다. 직원 8명이 동시에 접수해도 오류와 규칙 위반이 없었다. 단 확인과 저장을 트랜잭션 하나(`BEGIN IMMEDIATE`)로 묶었을 때만 그랬다.

## 선택지

**데이터를 어디에 둘지**
1. **호스트 PC 한 대가 DB 보관**: 다른 PC는 호스트에 접속해 화면만 보여준다.
2. **공유 폴더에 DB 파일**: 여러 PC가 같은 파일을 직접 연다. SQLite 파일이 깨질 위험이 크다.
3. **PC마다 DB, 서로 동기화**: 호스트가 꺼져도 쓸 수 있지만, 동시에 받은 신청이 충돌할 때 규칙이 깨지기 쉽다.

**호스트를 바꿀 때**
1. **파일로 내보내기 → 가져오기**: 옛 호스트에서 데이터 파일을 만들고 새 PC에서 가져온다.
2. **앱끼리 네트워크로 넘기기**: 버튼 하나로 넘기지만 도중에 끊겼을 때 처리가 복잡하다.

## 결정

- **호스트 PC 한 대만 DB를 갖는다.** 다른 PC의 앱과 브라우저는 호스트에 접속해서 쓴다.
- **호스트를 바꿀 때는 파일로 내보내고 가져온다.**

## 이유

- 데이터가 한 곳에만 있어서 "어느 PC 데이터가 최신인가" 같은 문제가 생기지 않는다.
- 업무 규칙 확인과 저장을 한 곳에서 트랜잭션 하나로 처리할 수 있다. 실험 01에서 확인한 방식 그대로다.
- 파일로 넘기는 방식은 백업과 같은 원리라 함께 만들 수 있고, 첫 버전에 넣기 쉽다.

## 결과

**좋은 점**
- 구조가 단순하다. 데이터 주인이 분명하다.
- 내보낸 파일이 그대로 백업이 된다.

**감수할 점**
- 호스트 PC가 꺼지면 다른 PC도 쓸 수 없다. 호스트는 접수 기간에 켜 두는 PC(예: 접수 담당 PC)로 정하도록 안내한다.
- 호스트가 고장 나면 마지막으로 내보낸(백업한) 시점까지만 되살릴 수 있다. 백업 방식은 4단계 10번에서 정한다.

**지켜야 할 것**
- **호스트가 둘이 되면 안 된다.** 옛 호스트와 새 호스트가 동시에 접수를 받으면 데이터가 갈라진다. 그래서
  - 데이터마다 고유 번호(데이터 묶음 ID)와 넘긴 횟수(세대 번호)를 둔다.
  - 넘기기용으로 내보내면 옛 호스트는 "넘김" 상태가 되어 더 이상 접수를 받지 않는다. 새 호스트는 가져올 때 세대 번호를 올린다.
  - 접속하는 PC는 세대 번호가 더 낮은 호스트를 만나면 경고한다.
  - 자세한 방식은 호스트 넘기기 기능을 만들 때(6단계) 정한다.
- 앱끼리 네트워크로 넘기는 방식은 필요해지면 나중에 추가한다.
