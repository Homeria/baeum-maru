# 0005. 저장소: SQLite + sqlx, 구조 변경은 자동 적용 + 사전 백업

- 상태: 채택 (2026-11-14)
- 근거: [실험 01](../../spikes/01-sqlite-concurrency/), [0002](0002-data-owner.md)

## 상황

호스트 PC 한 대가 DB를 갖는다(0002). 기관에는 IT 담당자가 없는 경우가 많아 DB 서버를 따로 설치하거나 관리할 수 없다. 새 버전에서 표나 칸이 바뀌어도(마이그레이션) 기존 데이터가 안전하게 넘어가야 한다.

실험 01: SQLite에서 직원 8명이 동시에 접수해도 오류와 규칙 위반이 없었다. 단 확인과 저장을 `BEGIN IMMEDIATE` 트랜잭션 하나로 묶어야 했다.

## 선택지

**DB 도구**
1. **sqlx**: SQL을 직접 쓴다. async, 마이그레이션 기능 포함. 실험 01에서 썼다.
2. **rusqlite**: 가장 단순하다. async가 아니고 마이그레이션은 따로 붙여야 한다.
3. **ORM (SeaORM, Diesel)**: Rust 코드로 DB를 다룬다. 배울 것이 많고 SQLite 세부 제어가 어렵다.

**구조 변경 적용**
1. **자동 적용 + 사전 자동 백업**
2. **관리자가 버튼으로 적용**

## 결정

- **DB는 SQLite, 도구는 sqlx.** SQLite는 실행 파일에 포함해 따로 설치하지 않는다.
- **구조 변경은 호스트가 새 버전으로 시작할 때 자동으로 적용한다.**
  - 적용 전에 DB를 자동으로 백업한다.
  - 적용에 실패하면 백업으로 되돌리고, 무엇이 실패했는지 알린다.
  - 한 번 배포한 구조 변경 파일은 고치지 않는다. 바꿀 일이 생기면 새 파일을 더한다.
- **확인하고 저장하는 쓰기 작업은 `BEGIN IMMEDIATE` 트랜잭션 하나로 묶는다** (실험 01).
- DB 설정: WAL 모드, 잠겨 있으면 잠시 기다리기(`busy_timeout`). 구체적인 값은 뼈대(5단계)에서 정한다.
  - 2026-11-15 정함: WAL, `synchronous=FULL`(정전 때 마지막 저장을 잃지 않게), `busy_timeout` 5초, 연결 8개, 외래 키 검사 켬. 실험 01은 `NORMAL`로 쟀다.

## 이유

- 실험 01에서 SQLite와 sqlx로 동시 접수를 확인했다.
- sqlx는 서버(axum)와 같은 async 방식이고 마이그레이션 기능이 들어 있어 도구를 덜 늘린다.
- SQL을 직접 쓰면 `BEGIN IMMEDIATE` 같은 SQLite 동작을 그대로 제어할 수 있다. 업무 규칙이 깨지지 않게 하는 핵심이다.
- 자동 적용은 IT 담당자 없이 업데이트만 하면 되게 해 준다. 사전 백업이 실패했을 때의 안전망이다.

## 결과

**좋은 점**
- 기관은 DB를 몰라도 된다. 데이터는 파일 하나라 백업과 호스트 넘기기(0002)가 쉽다.

**감수할 점**
- SQL을 직접 쓰므로 표가 많아지면 쿼리 작성량이 늘어난다.
- 구조 변경 파일을 고치지 않는 규칙을 지켜야 한다. 나중에 CI에서 자동으로 검사한다 (5단계).
- 옛 버전 앱이 새 구조의 DB를 열면 안 된다. 버전 확인 방식은 뼈대에서 정한다.
