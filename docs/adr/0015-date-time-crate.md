# 0015. 날짜·시각은 time crate로 다룬다

- 상태: 채택 (2026-11-22)
- 근거: [0005](0005-storage.md), [0012](0012-skeleton.md)

## 상황

날짜·시각을 다루던 `chrono`에 관리 중단 공지(RUSTSEC-2026-0543)가 올라왔다. 보안 구멍은 아니지만 앞으로 문제가 생겨도 고쳐지지 않는다. RustSec은 `jiff`와 `time`을 대안으로 권한다.

배움마루가 날짜·시각으로 하는 일은 셋이다.
- 날짜: 생년월일, 학기 기간, 직원 유효기간. DB에 `YYYY-MM-DD` 글자로 둔다.
- 시각: 만든·고친 시각, 세션의 마지막 요청, 계정 잠금, 접속 기록. UTC로 `2026-11-15T01:02:03.000Z` 모양의 글자로 둔다. SQL에서 글자끼리 크기를 비교하므로 모양이 늘 같아야 한다.
- 기관 PC의 지역 날짜: 유효기간이 지났는지 판단한다.

화면용 TypeScript 타입(ts-rs)에도 날짜 칸이 있다.

## 선택지

1. **time**: sqlx가 직접 지원한다(`time` 기능). ts-rs는 지원하지 않아 날짜 칸마다 TypeScript 타입을 적어 준다. 0.3에 오래 머물러 있지만 널리 쓰이고 관리된다.
2. jiff: 시간대 처리가 가장 정확하다. sqlx는 직접 지원하지 않아 `jiff-sqlx`의 감싼 타입을 거쳐야 하고, ts-rs는 옛 0.2만 지원해 1.0에는 쓸 수 없다. 기본으로 만드는 시각 글자는 소수점 자리가 들쭉날쭉하다.
3. chrono 유지: 할 일이 없지만 관리가 끊긴 crate에 날짜를 맡긴다.

## 결정

**날짜·시각은 `time`으로 다룬다.** chrono는 모든 crate에서 뺀다(sqlx의 `chrono`, ts-rs의 `chrono-impl` 기능도 끈다).

- 날짜는 `time::Date`, 시각은 `time::OffsetDateTime`을 쓰고 시각은 늘 UTC로 둔다. sqlx가 `OffsetDateTime`은 지원하지만 UTC 전용 타입(`UtcDateTime`)은 지원하지 않아서다.
- DB에 쓰는 시각 글자는 지금처럼 우리 함수 한 곳에서 밀리초 세 자리, `Z`로 고정해 만든다.
- JSON의 날짜는 `"2026-11-15"` 글자다(`serde-human-readable` 기능).
- 화면 타입의 날짜 칸에는 `#[ts(type = "string")]`을 적는다.
- 저장 모양은 바꾸지 않는다. 지금 글자 모양은 SQLite가 권하는 관례이고, DB를 열었을 때 사람이 읽을 수 있다.

## 이유

- sqlx가 직접 지원해서 DB에서 읽는 코드가 거의 그대로다. jiff는 읽는 구조체마다 감싼 타입이나 직접 변환이 필요하다.
- ts-rs는 time과 jiff 모두 쓸 수 없어 이 점은 차이가 없다.
- 배움마루는 한 기관, 한국에서 쓴다. 필요한 것은 날짜, UTC 시각, PC 지역 날짜뿐이라 jiff의 시간대 계산이 쓰일 데가 없다.
- 실험: 지금 저장한 시각·날짜 글자를 time으로 그대로 읽었고, 여러 스레드가 도는 중에도 지역 시각(+09:00)을 얻었다(Ubuntu).

## 결과

**좋은 점**
- 관리되는 crate로 옮기고 `deny.toml`의 예외를 지운다.
- DB 저장 모양과 API JSON 모양이 그대로다.

**감수할 점**
- 화면 타입의 날짜 칸마다 TypeScript 타입을 손으로 적는다. 빠뜨리면 생성 파일 검사(`check-bindings`)가 아니라 컴파일에서 걸린다.
- Windows에서 지역 시각을 얻는 것은 아직 확인하지 않았다. Windows 빌드에서 유효기간 판단을 확인한다.
- 시간대를 제대로 다뤄야 할 일(여러 지역 기관이 한 데이터를 쓰는 등)이 생기면 jiff를 다시 본다.
