# 0019. 웹사이트는 이 저장소의 site/에 두고 GitHub Actions로 Pages에 올린다

- 상태: 채택 (2026-11-23)
- 근거: [0010](0010-distribution.md), [0012](0012-skeleton.md)

## 상황

0010에서 안내 페이지를 GitHub Pages에 두기로 했다. 그 뒤 소개, 블로그, 다운로드 안내를 담는 웹사이트를 따로 만들기로 했다. 웹사이트는 코드 담당과 다른 에이전트(웹페이지·블로그 담당)가 맡는다.

정해야 할 것은 세 가지다.

- 사이트를 어느 저장소에 둘지
- Pages에 어떻게 올릴지
- 앱 검사와 어떻게 나눌지

앱은 아직 기능을 만드는 중(로드맵 6단계)이라 내려받을 출시본이 없다. 출시 전에 저장소를 조직 계정으로 옮길 수 있고, 그러면 사이트 주소가 바뀐다.

## 선택지

**저장소**

1. **이 저장소의 `site/`**: 선택 기록(`docs/choices/`), 용어집, ADR을 같은 저장소에서 읽고 대조할 수 있다.
2. **별도 저장소**: 앱과 이력이 섞이지 않는다. 대신 문서를 오가며 맞추기 어렵고 내용이 어긋나기 쉽다.

**Pages에 올리는 방식**

1. **GitHub Actions로 빌드해 바로 올림**: 빌드 결과물을 저장소에 커밋하지 않는다.
2. **`gh-pages` 브랜치에 결과물을 둠**: 결과물 커밋이 이력과 용량을 키우고, GitHub Flow(main과 작업 브랜치) 밖의 브랜치가 하나 생긴다.

## 결정

**이 저장소의 `site/`, GitHub Actions로 올린다.**

- 웹사이트 파일은 모두 `site/` 아래에 둔다.
- 사이트 워크플로는 앱 검사(`check.yml`)와 따로 둔다. 둘은 경로로 나눈다.
  - 앱 검사는 지금처럼 앱 경로만 본다. `site/`는 들어가지 않는다.
  - 사이트 검사는 `site/` 변경에만 돈다. 사이트 빌드, 내부 링크와 이미지 경로, 형식을 본다.
  - 외부 링크는 네트워크 상태에 따라 거짓 실패가 나기 쉬워 손으로 본다.
- Pages 배포는 평소에는 `site/` 변경이 main에 머지될 때와 수동 실행 때 한다. 앱 출시 태그로 바로 배포하지는 않는다.
- 공개 배포는 출시 준비 때 시작한다. 계정 위치가 정해지기 전에 임시 주소가 검색에 잡히지 않게 하려는 것이다. 그때까지는 사이트 검사만 돌리고, 확인은 각자의 PC에서 미리보기로 한다.
- 뼈대(소개, 블로그, 다운로드 안내 자리)는 출시 전에 만든다. 다운로드 칸은 출시 전까지 안내 상자로 둔다. 누를 수 없는 가짜 버튼은 두지 않는다.
- 스크린샷은 더미 데이터로만 찍고, 저장소가 커지지 않게 압축해서 넣는다.

정하지 않고 열어 두는 것:

- 사이트 생성 도구: 뼈대 이슈에서 후보를 비교해 고른다.
- 출시 버전과 다운로드 링크를 잇는 방법: 7단계 출시 준비에서 정한다. 릴리스 파일 이름 규칙이 아직 없다.
- `site/` 안의 폴더 구조와 이미지 형식·크기 상한: `site/README.md`에 둔다.

## 이유

- 앱의 동작과 사이트의 설명이 어긋나지 않는 것이 가장 중요하다. 같은 저장소면 선택 기록과 용어집을 바로 대조할 수 있다.
- 결과물을 커밋하지 않으면 이력이 깨끗하고 브랜치 규칙(0012)을 그대로 쓴다.
- 경로로 나누면 문서만 바뀔 때 앱 검사가 돌지 않는다는 규칙(0012)을 지키면서, 사이트도 따로 검사할 수 있다.

## 결과

**좋은 점**
- 사이트 작업과 앱 작업이 서로의 검사를 돌리지 않는다.
- 출시 전에 사이트 구조와 글을 미리 맞춰 볼 수 있다.

**감수할 점**
- 사이트 도구에 따라 `site/`에 따로 의존성이 생긴다. 정적 결과물만 올리므로 앱보다 위험은 작지만, 점검 대상이 늘어난다.
- 출시 전까지는 다른 기기(휴대폰 등)에서 사이트를 볼 수 없다.
