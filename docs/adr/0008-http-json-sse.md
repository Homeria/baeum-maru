# 0008. 화면과 서버의 대화: HTTP + JSON 요청, SSE 변경 알림

- 상태: 채택 (2026-11-14)
- 근거: [실험 03·04](../../spikes/03-tauri-ime-lan/), [0002](0002-data-owner.md), [0007](0007-app-only-access.md)

## 상황

DB는 호스트(A) 한 곳에만 있다(0002). 다른 PC(B, C)의 앱은 A에 접속해서 쓴다(0007).

이전 버전에서는 동기화가 프로젝트를 엎은 이유 중 하나였다. 예를 들어 B가 신청을 등록하면 A를 거쳐 C의 목록까지 갱신되어야 한다.

이 구조에서는 B, C가 데이터 사본을 갖지 않으므로 맞춰야 할 데이터가 없다. 남는 문제는 "다른 사람이 바꾼 내용을 화면이 어떻게 알고 새로 그리는가"뿐이다.

Tauri 전용 통신(IPC)은 같은 PC 안에서만 되므로 B, C와 이야기할 수 없다.

## 선택지

**요청**
1. **HTTP + JSON**: 실험 03의 `/api/echo`와 같은 방식
2. Tauri 전용 통신: 같은 PC 안에서만 됨

**변경 알림 (서버가 먼저 알려야 하는 일)**
1. **SSE (Server-Sent Events)**: 화면이 연결 하나를 열어 두고, 서버가 그 연결로 알림을 내려보낸다. 끊기면 다시 연결한다.
2. WebSocket: 양방향으로 열린 연결. 할 수 있는 것은 많지만 다루기가 더 복잡하다.
3. 주기적으로 물어보기(폴링): 단순하지만 늦게 반영되고 요청이 많다.

## 결정

- **모든 요청은 HTTP + JSON으로 한다.** 호스트 PC의 앱 창도 자기 서버(`127.0.0.1:47800`)에 같은 방식으로 요청한다. 호스트, 다른 PC 모두 같은 길을 쓴다.
- **변경 알림은 SSE로 한다.**
- **알림에는 데이터를 담지 않고 "무엇이 바뀌었는지"만 담는다.** 화면은 알림을 받으면 해당 데이터를 HTTP로 다시 받는다.

```text
① B → A   신청 저장 요청                     (HTTP)
② A       업무 규칙 확인 + 저장 (트랜잭션 하나)
③ A → 모두 "스마트폰 초급 1반 신청 목록 바뀜"  (SSE)
           → A의 창, B, C
④ 각 화면  해당 목록을 다시 요청             (HTTP)
```

- 연결이 끊겼다가 다시 붙으면 화면은 보고 있던 데이터를 전부 다시 받는다.
- Tauri 기능은 PC 자체 기능이 꼭 필요한 일(예: 파일 저장 위치 고르기)에만 쓴다.
- 알림 종류와 요청 주소(API 경로)의 이름 규칙은 뼈대(5단계)와 기능 슬라이스(6단계)에서 정한다.

## 이유

- 데이터의 주인이 하나이고 알림은 "새로 받아라"는 신호일 뿐이라, 알림을 놓쳐도 데이터가 틀어지지 않는다. 동기화 문제가 구조적으로 생기지 않는다.
- A도 다른 PC와 똑같이 자기 서버의 손님이라 "누가 등록했느냐"에 따라 경우를 나눌 필요가 없다.
- 알림은 서버→화면 한 방향뿐이라 SSE로 충분하다. 끊김 뒤 다시 연결하는 기능이 기본으로 있고 axum이 지원한다.

## 결과

**좋은 점**
- 이전 버전의 동기화 문제를 구조로 없앤다.
- 요청 방식이 하나라 서버 기능을 한 번만 만든다.

**감수할 점**
- 알림을 받을 때마다 다시 요청하므로 요청 수가 늘어난다. 직원 몇 명 규모에서는 문제되지 않는다 (실험 01 참고).
- SSE를 실제 앱(WebView2)에서 여러 PC로 시험하지는 않았다. 뼈대(5단계)에서 확인한다.

## 구현 메모

결정은 그대로다. 첫 구현(2026-11, 이슈 #72)에서 아래처럼 정했다.

- 알림 이름은 바뀐 데이터의 종류 하나다. 용어집의 영어 이름을 소문자와 밑줄로 쓴다(`member`, `application`, `priority_reason`). 어느 회원·강좌인지, 누가 바꿨는지는 담지 않는다. 화면은 종류마다 다시 받을 목록을 정해 둔다.
- 서버는 처리 함수마다 알림을 보내지 않는다. 주소를 등록할 때 그 주소가 바꾸는 종류를 붙여 두고, 읽기가 아닌 요청이 성공하면 그 종류를 알린다.
- 알림 연결(`GET /api/changes`)도 다른 요청처럼 승인된 기기에서 로그인한 직원만 연다. 화면이 잠기거나, 로그아웃하거나, 기기 승인이 취소되면 끊는다.
- 브라우저의 `EventSource`는 머리글을 실을 수 없어서, 화면은 `fetch`로 연결해 흐름을 읽는다. 기기 증표와 세션 증표를 다른 요청과 같은 머리글로 싣는다.
- 알림을 받거나 알림 때문에 다시 받는 요청은 화면 자동 잠금(BR-K8)의 시간을 늘리지 않는다.
