# 0006. 코드 나누기: 업무 규칙 crate + 앱 crate

- 상태: 일부 대체됨 ([0023](0023-code-layout.md): 앱 crate를 launcher·server로 나누기)
- 근거: [업무 규칙](../domain/BUSINESS_RULES.md), [0001](0001-app-form.md), [0005](0005-storage.md)

## 상황

Rust 코드는 crate(컴파일 단위)와 그 안의 모듈(폴더, 파일)로 나눈다.

- crate를 나누면 컴파일러가 경계를 지켜 준다. 예를 들어 업무 규칙 crate가 DB 도구에 의존하지 않으면, 규칙 코드에서 DB를 부르는 실수가 컴파일 오류가 된다.
- 대신 crate마다 설정 파일(`Cargo.toml`)이 생기고, crate 사이에서 쓰려면 공개 표시(`pub`)가 필요해 처음에는 헷갈린다.
- 유지보수자는 Rust를 배우면서 만든다. 아직 코드가 없어 경계를 미리 정확히 알기 어렵다.

참고로 어디까지가 관례인지:
- `Cargo.toml` + `src/main.rs` 또는 `src/lib.rs`: Rust 공식 관례
- Rust 코드를 `src-tauri/`에 두기: Tauri 관례
- 여러 crate를 `crates/` 아래에 두기: 큰 Rust 프로젝트에서 흔한 관례 (필수 아님)
- 역할마다 crate로 나누는 방식: 관례가 아니라 설계 선택

## 선택지

1. **crate 2개**: 업무 규칙만 떼고, 나머지는 한 crate에서 모듈로 나눈다.
2. **crate 1개**: 모두 모듈로 나눈다.
3. **crate 여러 개**: 업무 규칙, DB, 서버, 앱 창을 각각 crate로 나눈다.

## 결정

**1번. crate 두 개로 시작한다.**

```text
baeum-maru/
├── Cargo.toml        workspace (두 crate를 묶음)
├── crates/
│   └── domain/       업무 규칙 crate
└── src-tauri/        앱 crate (Tauri 관례 위치)
                      DB, 서버, 로그인, 앱 창을 모듈로 나눔
```

- **`domain` crate**: 용어집의 대상(회원, 강좌, 신청 등)과 업무 규칙(BR-…)을 담는다. DB, 서버, 앱 창 도구(sqlx, axum, tauri)에 의존하지 않는다.
- **앱 crate**: `domain`을 가져다 쓰고, DB 저장, 서버, 로그인, 앱 창을 모듈로 나눠 담는다.
- 의존 방향은 한쪽뿐이다: 앱 crate → `domain`. `domain`은 앱 crate를 모른다.
- 앱 crate가 커져서 경계가 분명해지면 그때 crate를 더 나눈다. 나눌 때는 ADR을 새로 쓴다.
- 모듈 이름과 파일 배치는 뼈대(5단계)에서 정한다.

## 이유

- 가장 중요한 경계는 "업무 규칙"과 "나머지"다. 업무 규칙은 이 프로그램의 핵심이고, DB나 화면 없이 테스트할 수 있어야 한다. 이 경계만 컴파일러에게 맡긴다.
- 나머지는 아직 코드가 없어 경계를 미리 정하면 틀리기 쉽다. 모듈로 시작해 실제로 커질 때 나누는 편이 싸다.
- crate가 둘뿐이라 Rust를 배우면서 다루기 부담이 작다.

## 결과

**좋은 점**
- 업무 규칙(BR-…)을 DB나 앱 없이 빠르게 테스트할 수 있다.
- 실험 코드(`spikes/`)는 workspace에 넣지 않고 지금처럼 따로 둔다.

**감수할 점**
- 앱 crate 안의 모듈 경계(예: 서버 코드가 DB 코드를 직접 부르지 않기)는 컴파일러가 아니라 사람이 지킨다. 필요하면 AGENTS.md 규칙이나 리뷰로 보완한다.
