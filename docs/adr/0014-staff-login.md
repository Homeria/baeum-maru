# 0014. 직원 확인 구현: argon2 PIN 해시, DB 세션, 잠금 값

- 상태: 채택 (2026-11-15)
- 근거: [0003](0003-login-access.md), [0005](0005-storage.md), [0007](0007-app-only-access.md)

## 상황

0003에서 로그인을 기기 승인과 직원 확인(이름 + PIN) 두 겹으로 정하고, 자동 잠금 시간과 허용 실패 횟수 같은 값은 기능을 만들 때 정하기로 했다. 직원 확인을 먼저 만든다. 기기 승인은 다른 PC가 호스트에 접속하는 기능과 함께 만든다.

정해야 할 것:
- PIN과 복구 코드를 DB에 어떤 모양으로 둘지
- 로그인 상태(세션)를 어디에 두고 어떻게 확인할지
- 잠금 값

## 선택지

**PIN 저장**
1. **argon2**: 비밀번호 저장에 지금 가장 많이 권하는 방식 (OWASP 1순위)
2. bcrypt: 오래 쓰인 방식. 충분히 안전하지만 새로 만들 때는 argon2를 더 권한다
3. PBKDF2: 표준 규격에 많이 들어 있지만, 같은 시간에 더 많이 대입해 볼 수 있어 약하다

**세션**
1. **DB에 세션 표**: 호스트가 증표의 해시와 마지막 요청 시각을 DB에 둔다
2. 호스트 메모리에만: 호스트가 꺼지면 모두 로그아웃된다. 여러 요청이 함께 바꾸는 값이라 공유 잠금이 필요하다
3. 서명된 토큰(JWT): 호스트가 저장하지 않고 서명으로 확인한다. 서버가 여럿인 서비스용이라 호스트 한 대에는 과하고, 중간에 끊기 어렵다

## 결정

**PIN 저장은 argon2, 세션은 DB 표로 한다.**

- PIN과 복구 코드는 argon2id로 해시해 저장한다. 설정값은 crate 기본값(OWASP 권고 범위)을 쓴다. 입력한 PIN은 로그와 접속 기록에 남기지 않는다.
- 로그인하면 호스트가 운영체제의 난수로 32바이트 증표를 만들어 앱에 준다. DB에는 증표의 SHA-256 해시만 둔다. 증표는 길고 무작위라 느린 해시가 필요 없고, 요청마다 확인해야 해서 빨라야 한다.
- 앱은 증표를 메모리에만 두고 요청마다 `Authorization: Bearer <증표>` 머리글로 싣는다. 앱을 끄면 다시 로그인한다.
- 요청마다 호스트가 세션과 직원 계정을 함께 읽는다. 그래서 역할 변경, 사용 중지, 유효기간 만료가 다음 요청부터 바로 적용된다.
- 마지막 요청에서 10분이 지난 세션은 잠긴다. 잠긴 세션은 잠금 풀기 요청만 받는다. 화면도 10분 동안 입력이 없으면 스스로 잠그지만, 판단의 기준은 호스트다.
- 복구 코드는 헷갈리는 글자(0과 O, 1과 I 등)를 뺀 대문자·숫자 16자를 4자씩 끊어 보여 준다. 예: `K7QF-M2XA-9TRE-HW4C`
- 로그인 화면은 고를 수 있는 직원의 이름과 역할을 보여 주고, 역할별로 묶는다. 자주 바뀌는 임시 직원이 많아도 이름을 찾기 쉽게 하기 위해서다. PIN 복구 화면에는 관리자만 보인다.

**값**

| 항목 | 값 |
|---|---|
| PIN 길이 | 숫자 4~8자리, 관리자는 6자리 이상 |
| 화면 잠금 | 마지막 요청에서 10분 |
| 계정 잠금 | 5번 연속 틀리면 5분 |

값은 코드의 상수로 둔다. 기관이 바꾸는 설정은 나중에 정한다.

**새 의존성**: `argon2`, `sha2`(둘 다 RustCrypto), `getrandom`. 라이선스는 cargo-deny로 확인한다.

## 이유

- 4자리 PIN은 경우의 수가 적어 DB 파일을 훔친 사람에게는 어느 해시든 오래 버티지 못한다. 그래도 해시로 두면 파일을 잠깐 본 사람이 PIN을 바로 읽지는 못한다. 실제 방어는 기기 승인과 틀리면 잠금이 맡는다 (0003).
- DB 세션은 이미 있는 DB 층과 테스트 방식을 그대로 쓴다. 잠금을 호스트가 판단하므로 화면을 조작해도 풀리지 않고, 관리자가 직원을 막으면 그 자리에서 끊긴다.
- 호스트가 다시 켜져도 세션 표는 남지만, 앱이 증표를 메모리에만 두므로 앱을 다시 켜면 새로 로그인한다. 남은 세션은 10분 뒤 잠기고 쓰이지 않는다.

## 결과

**좋은 점**
- 역할, 사용 중지, 유효기간이 요청마다 확인되어 바로 적용된다.
- 잠금과 틀린 횟수가 호스트에 있어서 앱을 다시 켜도 풀리지 않는다.

**감수할 점**
- 요청마다 DB를 한 번 더 읽는다. 호스트 한 대, PC 몇 대 규모에서는 문제가 되지 않는다.
- 같은 Wi-Fi에서 오가는 증표와 PIN은 엿볼 수 있다. 0003대로 7단계(TLS)에서 막는다.
- 오래된 세션 줄이 쌓인다. 로그인할 때 그 직원의 잠긴 세션을 지워 정리한다.
- 로그인 화면에서 누가 관리자인지 보인다. 지금은 호스트 PC에서만 열리고 다른 PC는 기기 승인을 거쳐야 하며(0003), 틀리면 잠금이 PIN 대입을 늦춘다.
