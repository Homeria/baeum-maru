## 상황

4단계에서 큰 구조를 정했다. 다음 내용은 뼈대(5단계)에서 정하기로 미뤄 두었다.

- 0009: JavaScript와 TypeScript 중 무엇을 쓸지, 화면 파일을 앱에 넣는 방법, 부품 라이브러리
- 0010: 포터블판과 설치판을 구분하는 방법, 버전을 맞춰 보는 방법
- 0007: 호스트가 화면 파일도 주지 않을지

코드를 쓰기 전에 검사 도구, 브랜치 운용, CI, 의존성 관리도 정해야 한다.

유지보수자의 기준은 가벼움과 안정성(버벅임 없음, 버그 적음)이다. 유지보수자는 혼자이고, React는 배운 적이 있으며, Rust는 배우는 중이다.

## 결정

### 화면

| 항목 | 결정 | 고르지 않은 것 |
|---|---|---|
| 언어 | **TypeScript** (`strict` 켬) | JavaScript |
| 화면 파일 위치 | **각 앱 안에 넣는다** (Tauri 기본). 호스트는 화면 파일을 주지 않는다 | 호스트가 화면을 보냄 (실험 03 방식) |
| 부품 | **직접 CSS(CSS Modules) + 필요한 곳만 headless 라이브러리** | 직접 CSS만, MUI·Ant Design, Tailwind + shadcn/ui |
| 서버 데이터 | **TanStack Query** | `useEffect` + `fetch` 직접 짜기 |
| 다시 그리기 최적화 | **React Compiler** | 손으로 `useMemo` 붙이기 |
| 자료형 맞추기 | **ts-rs** (Rust 구조체 → TS 자료형) | 손으로, specta, OpenAPI |

- 창의 화면(`http://tauri.localhost`)과 서버(`127.0.0.1:47800`)는 주소가 달라서, 서버가 CORS로 Tauri 창 주소만 허용한다. Tauri HTTP 플러그인은 SSE를 표준 방식으로 받을 수 없어 쓰지 않는다.
- **화면을 앱 안에 넣는 이유**
  - 기기 증표(0007)를 앱 안의 믿을 수 있는 화면만 다룬다. TLS를 7단계로 미룬 지금, 네트워크 너머 페이지에 앱 권한을 주지 않는다.
  - 호스트에 화면 파일이 없으니 브라우저로는 볼 것이 없다. 0007의 "앱으로만 접속"이 자연스럽게 완성된다.
  - 앱마다 화면 버전이 다를 수 있지만, 0010의 버전 규칙으로 해결한다.
- 어떤 headless 라이브러리를 쓸지(Radix UI, React Aria 등)는 대화 상자가 처음 필요해지는 6단계에서 고른다.
- TanStack Query의 기본 방식은 0008과 같다. 알림이 오면 해당 데이터를 "낡음"으로 표시하고 다시 받는다. 안 보이는 탭은 열 때 다시 받는다.
- ts-rs는 화면으로 보내는 응답 구조체(앱 crate)에만 붙인다. 업무 규칙 crate에는 붙이지 않는다. 생성한 TS 파일은 레포에 올린다. CI는 다시 생성했을 때 올린 파일과 다르면 실패한다.

### 화면 구성 규칙

**화면 크기와 이동**
- 기준 화면은 1920×1080, 글자 크기 100%다. 이 크기에서 스크롤 없이 보이게 만든다.
- 더 작은 화면이나 글자를 키운 PC에서는 화면이 깨지지 않고 표의 줄 수만 줄어든다.
- 화면 이동은 메뉴 탭(예: `[회원] [강좌] [신청] [선발]`)으로 한다.

**큰 목록**
- 검색과 페이지 나누기로 보여 준다.
- 검색과 페이지 자르기는 호스트가 한다. 화면은 한 페이지 분량과 전체 건수만 받는다.
- 한 페이지 줄 수는 화면 높이로 계산한다. 0009의 상한(1,000줄)보다 훨씬 적다.

**컴포넌트화**
1. 공용 부품(`ui/src/components/`)은 업무를 모른다. 받은 값만 그린다.
2. 기능 화면(`ui/src/features/`)은 공용 부품을 조립만 한다. 필요한 부품이 없으면 공용 부품에 먼저 추가한다.
3. 색, 글꼴, 간격은 한 곳(CSS 변수)에만 정하고, 부품 CSS는 그 변수만 쓴다.
4. 부품 하나에 폴더 하나를 쓴다(`.tsx`, `.module.css`, 테스트).

**최적화**
1. 표는 페이지를 나눈다.
2. 목록의 key는 데이터 ID로 한다.
3. `useMemo`와 `memo`는 React Compiler에 맡긴다. 손으로 붙이는 것은 재 봐서 필요할 때만 한다.

### 폴더 구조

```text
baeum-maru/
├─ Cargo.toml            Rust workspace
├─ rust-toolchain.toml   Rust 버전 고정
├─ justfile              검사·개발 명령
├─ crates/domain/        업무 규칙 crate (0006)
├─ src-tauri/            앱 crate: 서버, DB, 창 (0006)
├─ ui/                   화면 (React + TypeScript + Vite)
│  └─ src/
│     ├─ components/     공용 부품
│     ├─ features/       기능별 화면
│     ├─ api/            요청 주소, SSE, 생성된 자료형
│     └─ app/            시작, 메뉴 탭, 전역 스타일
├─ docs/  spikes/
└─ .github/
```

- Tauri 템플릿은 화면 코드를 맨 위 `src/`에 둔다. 배움마루는 Rust 파일과 섞이지 않도록 `ui/`로 뺀다.

### 포터블판과 버전

**포터블판 구분**
- exe 옆에 `data` 폴더가 있으면 포터블판으로 동작하고, 데이터를 그 안에 둔다. VS Code 포터블 모드와 같은 방식이다.
- 포터블판 ZIP에는 빈 `data` 폴더를 넣어 낸다.

**설치판 데이터 위치**
- Windows 계정별 앱 데이터 폴더(`%APPDATA%`)를 쓴다(Tauri 관례).
  - 폴더 이름은 앱 식별자 `io.github.homeria.baeummaru`다(안내 페이지 주소 `homeria.github.io`를 뒤집은 것). 바꾸면 데이터 폴더가 바뀌므로 바꾸지 않는다.
- 첫 실행 화면과 관리 화면에서 데이터 위치를 보여 준다. 계정이 다르면 데이터도 다르기 때문이다.

**버전 맞춰 보기**
- 호스트에 접속할 때 버전을 확인한다. 이 확인 주소는 기기 승인 없이도 응답하고, 버전 번호만 알려 준다.
- 모든 요청에도 버전을 싣는다. 호스트는 앞 두 자리가 다르면 거절한다. 그래서 앱을 켜 둔 채 호스트만 업데이트돼도 바로 잡는다.
- 버전 번호는 workspace `Cargo.toml` 한 곳에만 적는다. Tauri 설정과 화면은 거기서 읽는다.
- 1.0 이전에는 `0.둘째.셋째`를 쓰고 같은 규칙을 적용한다.

### 검사 도구와 버전 고정

**검사 도구**

| 대상 | 도구 |
|---|---|
| Rust | `rustfmt`, `clippy` (CI에서 경고를 오류로: `-D warnings`), `cargo test` |
| 화면 | Prettier, ESLint(React Compiler 규칙 포함), TypeScript 검사 |
| 의존성 | cargo-deny (보안 취약점, 라이선스 허용 목록, 출처) |

- **명령 하나로 전부 검사한다: `just check`.** CI도 같은 명령을 쓴다.
- 커밋 전 자동 검사(git hook)는 넣지 않는다.

**버전 고정**
- Rust: `rust-toolchain.toml`에 `1.100.0`으로 고정한다. 올릴 때는 별도 PR로 올린다.
- Node: `.node-version`에 22로 고정한다. 2027년 4월 지원 종료 전에 올린다.
- 패키지 관리자: npm. `package-lock.json`을 레포에 올린다.

### 브랜치와 CI

**브랜치: GitHub Flow**
- main은 늘 동작하는 상태로 둔다. main에 직접 커밋하지 않고 PR로만 합친다.
- 작업 브랜치 이름은 커밋 종류와 맞춘다: `feat/…`, `fix/…`, `refactor/…`, `docs/…`, `chore/…`. 이슈 템플릿 종류도 같다.
- PR은 Squash로 합친다. main 기록은 "PR 하나 = 커밋 한 줄"이 된다.
- 출시는 main에 태그(`v0.1.0`)를 붙여서 한다. 급한 수정도 같은 길이다(`fix/…` → PR → 셋째 자리를 올린 태그).
- release, develop 브랜치는 두지 않는다. 옛 버전은 지원하지 않는다(0010).
- main 보호는 "PR 필수"만 켠다.
  - "검사 통과 필수"는 켜지 않는다. 문서만 고친 PR은 검사가 돌지 않아 합치기가 잠기기 때문이다.

**워크플로**

| | 검사 (`check.yml`) | Windows 빌드 (`release.yml`) |
|---|---|---|
| 언제 | main으로 가는 PR, main에 push. **적어 둔 경로가 바뀐 때만** | `v*` 태그 push, Actions 화면에서 직접 실행 |
| 실행 환경 | Ubuntu | Windows |
| 하는 일 | `just check` | 설치판(NSIS)과 포터블판(ZIP) 빌드 |
| 결과 | 통과 / 실패 | 태그면 릴리스 **초안**, 직접 실행이면 시험용 파일 |

- 검사가 도는 경로는 이것만 적는다. 이 경로 안이라도 `*.md`는 뺀다.
  - `crates/**`, `src-tauri/**`, `ui/**`
  - `Cargo.toml`, `Cargo.lock`, `rust-toolchain.toml`, `justfile`, `deny.toml`
  - `.github/workflows/**`
- 목록에 없는 `docs/`, `spikes/`, README, 템플릿을 고쳐도 아무것도 돌지 않는다.
- 같은 브랜치에 새로 push하면 돌던 검사를 취소한다. 빌드 결과는 캐시한다.
- 실험용 워크플로를 만들면 목적을 다한 뒤 바로 지운다.

### 의존성 관리

- **Dependabot**: 한 달에 한 번, Rust·npm·GitHub Actions를 종류별로 한 PR에 묶는다. 보안 알림은 켜고, 보안 업데이트는 기다리지 않고 바로 받는다.
- **cargo-deny**: `just check`에 넣는다. 라이선스 허용 목록 밖의 라이브러리가 들어오면 실패한다. 허용 목록은 MIT, Apache-2.0, BSD 등이다.
- **화면 라이브러리**: 넣을 때 사람이 라이선스를 확인한다. PR 템플릿에 "새 의존성: 이름과 이유" 칸이 있다.
- **`npm audit`**: 쓰지 않는다. 개발용 도구의 경고까지 쏟아져서 경고에 무뎌진다.

## 이유

- 성능 차이가 작은 곳(부품 라이브러리 등)은 가벼움, 고치기 쉬움, 덜 묶임을 기준으로 골랐다.
- 버그가 생기기 쉬운 곳은 검증된 도구에 맡겼다.
  - 자료형 어긋남: TypeScript, ts-rs
  - 데이터 다시 받기: TanStack Query
  - 다시 그리기: React Compiler
  - 키보드·포커스: headless 라이브러리
- 혼자 운영하고 옛 버전을 지원하지 않으므로 가장 단순한 브랜치 방식을 골랐다.
- 문서 변경에 빌드가 도는 일이 없도록, CI는 돌 경로만 적는 방식으로 했다.

## 결과

**좋은 점**
- 서버와 화면이 어긋나면 빌드 단계에서 잡힌다.
- 검사가 명령 하나라서 내 PC와 CI 결과가 같다.

**감수할 점**
- 개발 PC에 `just`를 따로 설치해야 한다.
- 화면 쪽 도구가 늘었다(TanStack Query, React Compiler, ESLint, Prettier). 대신 각각이 버그 한 종류씩을 막는다.
- React Compiler를 쓰려면 Vite 8에서 Babel 플러그인을 추가로 설정해야 하고, 빌드가 조금 느려진다.
- 문서만 고친 PR은 검사 없이 합쳐진다. 코드가 섞인 PR인지는 사람이 확인한다.
