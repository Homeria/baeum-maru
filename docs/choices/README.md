# 선택 기록

기능을 만들며 고른 것을 남긴다. 무엇을 정해야 했는지, 후보가 무엇이었는지, 왜 그것을 골랐는지만 적는다.

- 블로그와 다운로드 페이지의 글감이다. 주 독자는 기관 직원과 도입을 검토하는 사람이다. 여기서는 사실과 이유만 적고, 읽는 사람에 맞게 풀어 쓰는 일은 블로그 담당이 한다.
- 사용자 앞에서 왜 이렇게 동작하는지(안전, 개인정보, 실수 방지, 편의)가 드러나는 선택을 남긴다. 내부 구조만 바꾸는 선택(리팩터링, 모듈 나누기)은 남기지 않는다.
- ADR과 다르다. ADR은 프로젝트 전체가 따르는 기반 결정이고, 바꾸려면 새 ADR이 필요하다. 선택 기록은 기능 하나 안에서 고른 것이고, 나중에 바뀌어도 기록을 고치지 않는다.
- 파일 하나가 이슈 하나다. 이름은 `<이슈 번호 네 자리>-<브랜치의 하는 일>.md`다 (예: `0054-broken-db-restore.md`).
- 실제 기관 이름과 회원 정보는 쓰지 않는다.

## 형식

```markdown
# 제목 (#이슈 번호)

무엇을 만들었는지 한두 문장.

- 관련: ADR, 업무 규칙(BR-… 또는 역할별 표), 화면·탭 이름(화면에 보이는 글자 그대로)
- 사용자 흐름: 직원이 보는 화면과 누르는 버튼을 순서대로
- 알아둘 점: 일부러 넣지 않은 기능, 제한
- 웹페이지 안내: 바꿀 안내와 바뀐 내용 한 줄. 없으면 "없음"

## 정해야 했던 것

- 후보: A, B, C
- 고른 것: B
- 이유: 짧게. 버린 후보의 문제도 한 줄.
```

- 관련, 사용자 흐름, 알아둘 점은 파일 맨 위에 한 번만 쓴다. 어떤 선택이 따로 예외 화면이나 안내를 만들면 그 항목의 이유에 한 줄 덧붙인다.
- 웹페이지 안내: 설치, 업데이트, 데이터·백업 위치, 주요 화면 흐름이 바뀌면 적는다. 같은 줄을 PR 본문에도 적는다.
- 이유에 사실을 적으면 근거를 괄호로 붙인다. 바깥에 내는 글에서 부풀리지 않기 위해서다.
  - (잰 값: 수치, 환경)
  - (테스트로 확인)
  - (직접 확인): 유지보수자가 앱을 실행해 본 것
  - (원리만): 재거나 확인하지 않고 동작 원리로 말한 것
