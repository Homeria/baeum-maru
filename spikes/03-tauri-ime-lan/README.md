# 실험 03·04: Tauri 한글 입력과 다른 기기에서 접속

> 버린 코드다. 결론을 얻기 위한 실험이며 유지보수하지 않는다.

두 실험을 앱 하나로 한다. 앱을 켜면 앱 안에서 작은 웹 서버가 뜨고, 앱 창과 다른 기기의 브라우저가 같은 화면을 연다.

## 확인할 것

**실험 03: 한글 입력 (Windows, WebView2)**
1. 일반 입력칸, 여러 줄 입력칸에서 한글이 씹히거나 두 번 들어가지 않는가
2. 입력하자마자 반응하는 칸(검색칸)에서 조합 중인 글자가 이상하게 보이지 않는가
3. 한글을 치고 바로 Enter를 눌렀을 때 마지막 글자가 한 번 더 들어가지 않는가 (보호 없는 칸과 보호한 칸 비교)
4. 한글이 앱 안 서버를 거쳐도 깨지지 않는가

**실험 04: 다른 기기에서 접속**
1. 처음 실행할 때 Windows 방화벽 창이 뜨는가, 무엇을 눌러야 하는가
2. 같은 Wi-Fi의 휴대폰 브라우저로 화면에 나온 주소에 들어갈 수 있는가
3. 휴대폰에서도 한글 입력과 서버 왕복이 되는가

**덤: Windows 배포**
1. GitHub Actions에서 Windows 실행 파일을 만드는 데 얼마나 걸리고, 파일은 얼마나 큰가
2. 내려받은 `.exe`를 처음 실행할 때 SmartScreen 경고("Windows의 PC 보호")가 뜨는가

## 방법

- 앱: Tauri 2.12 (Windows에서는 WebView2로 화면을 그림), 서버: axum 0.8
- 서버는 `0.0.0.0:47800`(이 PC의 모든 네트워크 주소)에서 뜬다. 포트가 쓰이고 있으면 빈 포트를 쓴다.
- 앱 창은 `http://127.0.0.1:47800`을 연다. 화면에 다른 기기용 접속 주소가 나온다.
- Windows 실행 파일은 실험용 GitHub Actions 워크플로(`spike-windows-build.yml`)로 만들었다. 실험이 끝나 지웠고, git 기록에 남아 있다.
  - 교훈: 실험 폴더 전체를 빌드 조건으로 걸었더니 결과 문서만 고쳐도 빌드가 돌았다. 정식 CI에서는 빌드 조건을 코드 파일로 좁혀야 한다.
- Ubuntu에서는 Windows 대상으로 코드 검사(`cargo check`)만 했다. 이 PC에 Linux용 Tauri 라이브러리와 Windows 리소스 컴파일러가 없어서, 리소스 컴파일러는 빈 파일을 만드는 가짜로 대신했다.

## 결과

2026-11-14, Windows 11 (듀얼부팅 미니PC), 같은 Wi-Fi의 Android 휴대폰.

**빌드**
- GitHub Actions `windows-latest`에서 첫 빌드 4분 12초 (캐시 없음), 성공
- 실행 파일 9.0MB, 내려받는 압축 파일 2.8MB

**내려받기와 첫 실행**

| 단계 | 일어난 일 |
|---|---|
| Chrome으로 내려받기 | **바이러스로 취급해 차단.** 차단을 임시로 풀고 받았다 |
| 처음 실행 | **SmartScreen 창("Windows의 PC 보호")이 떴다.** "추가 정보 → 실행"으로 실행했다 |
| 서버 시작 | **Windows 방화벽 창이 떴다.** "허용"을 눌렀다 (개인/공용 네트워크 중 무엇이었는지는 기록하지 못함) |

**실험 03: 한글 입력 (앱 창, WebView2)**
- 시험 1~5 모두 문제없었다. 글자가 씹히거나 두 번 들어가는 일이 없었다.
- 시험 4-가(조합 중 Enter 보호 없음)에서도 마지막 글자가 한 줄 더 생기지 않았다.

**실험 04: 다른 기기에서 접속**
- 삼성 인터넷: 접속, 화면 표시 모두 정상
- **휴대폰 Chrome: "Too Many Requests"가 떠서 열리지 않았다.** 원인은 확인하지 못했다.
  - 이 오류(HTTP 429)는 실험 앱이 보내지 않는다. 서버(axum)에 요청 수 제한이 없다.
  - 그래서 Chrome 쪽 기능(HTTPS로 자동으로 바꿔 접속하기, 데이터 절약, 보안 검사 등)이나 휴대폰의 네트워크 설정(VPN, 사설 DNS) 같은 중간 단계가 의심되지만, 추측이다.

## 결론

- **Tauri(WebView2)로 한글 입력은 문제없다.** 직원 PC의 Edge와 같은 엔진이라 평소 쓰던 대로 입력된다. 조합 중 Enter 보호는 다른 브라우저(웹 접속)를 위해 계속 넣는다.
- **앱 안에 서버를 띄우고 같은 Wi-Fi의 다른 기기가 접속하는 구조는 된다.** 다만 처음 한 번 방화벽 허용이 필요하다.
- **배포의 가장 큰 걸림돌은 기능이 아니라 "믿을 수 있는 프로그램"으로 인정받는 일이다.** 서명하지 않은 실행 파일은 Chrome 내려받기 차단 → SmartScreen 경고 → 방화벽 허용, 세 번의 관문을 지난다. IT 담당자가 없는 기관 직원에게는 여기서 포기할 만한 장벽이다. 4단계(배포 방식)와 7단계(릴리스)에서 다뤄야 한다. 검토할 방향: 코드 서명, Microsoft Store 배포, 설치 안내서, 방화벽 규칙을 설치 과정에서 등록하기.

## 남은 확인

- **휴대폰 Chrome의 "Too Many Requests"** 원인. 웹으로 접속하는 예비 방식을 쓰려면 가장 흔한 브라우저인 Chrome에서 되어야 한다. 다시 시도할 때 주소창이 `http://`인지 `https://`로 바뀌었는지, 다른 휴대폰이나 PC의 Chrome에서도 같은지 확인한다.
- 방화벽 창에서 고른 네트워크 종류(개인/공용). 기관 Wi-Fi가 "공용"으로 잡혀 있으면 다른 기기가 못 들어올 수 있다.
- **관리자 권한이 없는 직원 계정**에서 방화벽 허용이 되는지. 기관 PC는 직원 계정에 관리자 권한이 없는 경우가 있다.
