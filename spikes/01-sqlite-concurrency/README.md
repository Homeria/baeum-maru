# 실험 01: SQLite 동시 저장

> 버린 코드다. 결론을 얻기 위한 실험이며 유지보수하지 않는다.

## 확인할 것

서버 프로그램 하나가 SQLite DB를 갖고 여러 직원의 접수를 동시에 받을 때,

1. "DB가 잠겨 있음" 오류가 생기지 않는가
2. 업무 규칙(BR-A3 최대 신청 개수, BR-A4 같은 강좌 중복 금지)이 깨지지 않는가
3. 신청 한 건 저장이 충분히 빠른가

공유 폴더에 DB 파일을 두고 여러 PC가 직접 여는 방식은 파일 손상 위험 때문에 처음부터 대상에서 뺐다.

## 방법

- 가짜 회원 300명, 강좌 30개 (번호뿐인 데이터)
- 직원 8명을 흉내 낸 동시 작업 8개가 각각 신청 500건, 모두 4,000건을 넣는다.
- 모든 직원이 같은 순서로 회원을 돌아가며 접수한다. 같은 회원을 여러 직원이 거의 동시에 접수하는 최악의 경우를 일부러 만든 것이다.
- 신청마다 같은 강좌 중복과 최대 4개를 확인한다.
- DB 설정: WAL 모드, `synchronous=NORMAL`, 잠겨 있으면 최대 5초 기다림(`busy_timeout`), 연결 8개
- 두 방식을 비교한다.
  - **Safe**: `BEGIN IMMEDIATE` 트랜잭션 하나 안에서 확인하고 저장한다.
  - **Unsafe**: 개수를 확인한 뒤 따로 저장한다.

## 결과

2026-11-14, Ubuntu 미니PC에서 세 번 실행. 세 번 모두 비슷했다.

| 항목 | Safe | Unsafe |
|---|---|---|
| 잠금 오류 | 0건 | 0건 |
| BR-A3 위반 회원 | **0명** | **55~79명** (한 회원 최대 8개) |
| 저장 시간 중간값 | 0.05ms | 0.03ms |
| 저장 시간 느린 쪽 1% | 3.7~8.2ms | 3.4~5.6ms |
| 저장 시간 최대 | 180~229ms | 34~79ms |
| 4,000건 전체 | 약 0.3초 | 약 0.13초 |

통과 기준(잠금 오류 0건, 규칙 위반 0명, 느린 쪽 1%가 100ms 이내)을 Safe 방식이 모두 만족했다.

실제 부하는 이보다 훨씬 작다. 직원 8명이 손으로 입력하면 많아야 몇 초에 한 건인데, 이 실험은 초당 1만 건이 넘는 속도로 넣었다.

## 결론

- **SQLite는 직원 여러 명의 동시 접수를 충분히 감당한다.** 서버 하나가 DB를 갖는 구조라면 별도 DB 서버가 필요 없다.
- **확인과 저장은 반드시 `BEGIN IMMEDIATE` 트랜잭션 하나로 묶어야 한다.** 따로 하면 오류는 전혀 나지 않으면서 규칙만 조용히 깨진다(Unsafe 결과). 오류가 없다고 안전한 게 아니다.
- 같은 강좌 중복(BR-A4)은 DB의 `UNIQUE` 제약으로도 한 번 더 막을 수 있다.

## 남은 확인

- Safe의 최대 저장 시간 약 0.2초는 원인을 보지 않았다. 다른 직원을 기다린 시간이나 WAL 정리(checkpoint)로 추정한다. 직원이 체감할 수준은 아니다.
- **Windows와 느린 디스크(HDD)에서는 다시 돌려 봐야 한다.** 이 결과는 SSD 미니PC의 Ubuntu에서 나왔다. 기관 PC는 더 오래되고 느릴 수 있다.

## 실행 방법

```sh
cargo run --release          # Safe와 Unsafe 모두
cargo run --release -- safe  # 하나만
```

실행하면 이 폴더에 `spike.db`가 생긴다. git에는 올라가지 않는다.
