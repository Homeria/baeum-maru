# 실험 06: 화면 기술 비교 (React vs Svelte)

> 버린 코드다. 결론을 얻기 위한 실험이며 유지보수하지 않는다.

## 확인할 것

화면 기술(4단계 7번)을 고르는 기준은 **경량화**와 **버벅임 없는 동작**이다. 같은 화면을 React와 Svelte로 만들어

1. 빌드한 파일 크기
2. 첫 표시 시간 (페이지를 열고 표가 보일 때까지)
3. 검색할 때 표가 다시 그려지는 시간
4. 알림(0008의 SSE)을 받고 목록을 새로 받아 표를 다시 그리는 시간

을 잰다.

## 방법

- 화면: 가짜 회원 표(6칸) + 검색칸 + 알림 갱신. 두 앱이 같은 데이터와 같은 측정 코드(`shared/`)를 쓴다.
- 두 앱 모두 흔히 짜는 방식 그대로 짰다. React에 최적화용 `memo`를 따로 넣지 않았다.
- 버전: React 19.3, Svelte 5.57, Vite 8.3. 빌드 결과는 HTML 파일 하나(`dist/index.html`)로 만든다.
- 측정(`shared/bench.js`), 같은 조작을 반복한다:
  - **검색→화면**: 검색어를 바꾸고 바뀐 표가 화면에 그려질 때까지. 화면 그리기를 기다리므로 60Hz 화면의 프레임 두 개(약 33ms)가 바닥값이다.
  - **알림→화면**: 목록 JSON을 해석하고 표가 화면에 그려질 때까지. 바닥값은 같다.
  - **DOM 처리**: 화면 도구가 표(DOM)를 고치는 데만 걸린 시간. 프레임을 기다리지 않아 도구 사이의 차이가 드러난다.
- `run-bench.mjs`가 Chrome을 화면 없이 띄워 두 앱을 3번씩 돌리고 중앙값을 낸다. CPU 감속(오래된 PC 흉내)과 표 줄 수 제한(페이지 나누기 흉내)을 줄 수 있다.
- 서버와 네트워크는 빼고 화면 쪽만 쟀다. 사무실 네트워크 왕복은 몇 ms 수준이다.

## 결론

- **버벅임을 가르는 것은 화면 도구보다 "한 번에 그리는 줄 수"다.** 오래된 PC 흉내에서 표에 1,000줄을 다 그리면 두 도구 모두 검색 한 번에 최대 0.3~0.4초가 걸렸다. 100줄만 그리면 회원이 5,000명이어도 두 도구 모두 프레임 바닥값(약 33ms)에 붙었다. 큰 표에는 **페이지 나누기를 반드시 넣는다.**
- **Svelte가 더 가볍고 조금 더 빠르다.**
  - 파일 크기 약 1/5
  - 첫 표시 25~40% 빠름 (오래된 PC 흉내 + 100줄: 87ms vs 139ms)
  - 많은 줄을 다룰 때 DOM 처리가 1.5~4배 빠름. 다만 페이지 나누기를 하면 차이가 몇 ms로 줄어 사람이 느끼기 어렵다.
- **React도 이 앱 규모에서는 충분하다.** 페이지 나누기를 하면 체감 차이는 첫 표시 0.05초 정도다. React의 강점(자료, 부품, AI 도움)은 이 측정에 드러나지 않는다.

## 남은 확인

- Windows(WebView2) 실측. Edge는 같은 엔진이라 비슷할 것으로 보지만 재지 않았다.
- 실제 오래된 기관 PC. CPU 감속은 흉내일 뿐이다.
- 한글 입력 중 검색(조합 중인 글자)은 자동 측정에 넣지 않았다. 사람이 쳐 보는 것으로 확인한다.

## 실행 방법

```sh
cd react && npm install && npm run build && cd ..
cd svelte && npm install && npm run build && cd ..
node run-bench.mjs 3          # 보통 속도
node run-bench.mjs 3 4        # CPU 4배 감속
node run-bench.mjs 3 4 100    # CPU 4배 감속 + 표 100줄
```

Windows에서는 `react/dist/index.html`, `svelte/dist/index.html`을 Edge로 열고 "자동 측정"을 누른다. 회원 수는 주소 끝에 `?n=5000`, 표 줄 수는 `&limit=100`을 붙여 바꾼다.
